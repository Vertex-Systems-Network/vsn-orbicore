## Implemented and tested

1. **Audit helper not accessible to SQL runtime callers.** `db/migrations/009_postgres_ci_auth_audit.sql` adds a controlled SECURITY DEFINER tenant audit helper, matching migration 006's PostgreSQL advisory lock and `audit_sequence` ordering. Auth events have fixed redacted metadata. Audit actor and tenant come from the real PostgreSQL session+user join; SQL input cannot pick another actor/tenant or supply a free-form audit message.
2. **Atomic audited wrappers.** Three guarded `SECURITY DEFINER` wrappers invoke migration 008's original PostgreSQL password login, recovery-code MFA/session rotation and logout respectively, and append an auth event **within the same SQL transaction**. If the final audit write is denied, the entire session creation, one-time recovery-code consumption and rotated token, or session revocation rolls back.
3. **No unaudited role bypass:** migration 009 revokes the restricted NOLOGIN submitter role's EXECUTE on migration 008's unaudited auth functions and on the audit helper; PUBLIC EXECUTE is revoked. Its only allowed auth operations are audited wrappers. A disposable real `LOGIN NOINHERIT NOBYPASSRLS` role with explicit SET-role membership cannot directly read passwords, session digests, recovery hashes or audit details or directly invoke the old unlogged entrypoints. `createPostgresCiLoginAdapter(pool,{audited:true})` chooses only the three versioned audited SQL functions; the original migration 008 integration remains separately tested without applying migration 009.
4. **Canonical SHA chain:** `auth.login.success`, `auth.login.mfa_pending`, `auth.mfa.recovery` and `auth.logout` events use fixed methods and exact raw JSON serialized text. Each event matches Node's existing `computeAuditEntryHash` algorithm. The hosted test confirms predecessor links across auth and interleaved `job.enqueue` events, across two tenants, beginning with a verified pre-existing legacy-compatible audit head. Raw passwords, cookie values, hashed sessions and recovery-code values are not stored in audit details.
5. **Redaction and fail-closed cases:** unknown/wrong-password attempts enter a separate pseudonymous PostgreSQL rate-limit store (no authenticated tenant available) rather than manufacturing tenant audit events. Viewer login is audited but remains unable to submit synthetic jobs. Cross-tenant job use and pending-MFA operations are refused. An unchained legacy audit head blocks a later login.
6. **Fault-injected recovery and rollback:** real PostgreSQL `NOT VALID` CHECK constraints were temporarily used to reject new login, MFA completion and logout audit rows. Login returned sanitized HTTP 503 with no new session; MFA returned sanitized HTTP 503 with the original pending session and unused code intact; logout returned sanitized HTTP 503 with the cookie still active. Removing the synthetic constraint allowed the same legitimate operation to succeed. Existing jobs/outbox and other tenants' chains were unaffected.
7. **Test-found JSON fidelity issue fixed:** first hosted integration failed because the *test seed* reused the same bind parameter as JSONB and raw JSON TEXT, allowing PostgreSQL JSONB key normalization to alter the raw audit string (Node SHA mismatch). The test now binds distinct `$5::jsonb` and `$6::text` values, preserving raw source JSON exactly; a second hosted integration independently passed every tenant audit hash. The regression check remains strict rather than suppressing mismatches.

## Important limits

- **Only the disposable PostgreSQL CI auth path is covered.** The existing `createApp` normal HTTP flow still authenticates SQLite scrypt users. PostgreSQL migration 008 uses explicitly tagged **CI bcrypt-only fixture** credentials; copying salted SQLite hashes alone cannot make them usable by its bcrypt login verifier.
- **No full authentication failure audit.** Unknown-email or wrong-password attempts are rate-limited via a SHA-256 digest of normalized email, not inserted into the per-tenant audit chain. This is not a keyed HMAC, not safe against offline email enumeration, and does not prove privacy-preserving enterprise-wide login-failure monitoring. Operational change and privileged-action audit unification are still open.
- **No production deployment proof.** The SQL wrappers are owned by the disposable schema owner. Real DB login governance, failover, retention/WORM/off-host audit archive, time-of-check production cookie behavior, hostile SQL access, production TLS reverse proxies and multi-writer migration are not proven.
- **No credential/key migration.** Existing SQLite scrypt hashes, encrypted TOTP/passkeys, recovery/notification channels, jobs, secret references and audit history are not migrated to production PG; reversible cutover, rollback, off-host restore and provider-authorized operations remain unsupported.
- ORB-005 stays `in_progress / integration_tested`; ORB-004 and ORB-016 remain `testing / integration_tested`.
