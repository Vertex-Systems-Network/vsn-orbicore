## Implemented guarantees in the opt-in synthetic worker

1. New idempotently reapplicable [migration 014](../../db/migrations/014_postgres_ci_signal_rejections.sql) adds a tenant-bound PostgreSQL `job_signal_rejections` table with forced RLS and no public/readonly SELECT policy; only `organization_id`, Redis **server-generated stream entry ID**, enum reason `tenant_mismatch` / `invalid_job_id` / `missing_job`, synthetic worker ID, timestamps and occurrence counter are stored. It contains **no raw Redis fields, rejected job ID, third-party tenant spoofing strings, password, email, payload, provider command or credential**.
2. [Redis consumer](../../apps/api/synthetic-redis-worker.mjs) now inserts the redacted reason in PostgreSQL **before** `XACK`; a PostgreSQL failure leaves the event unacknowledged in the Redis consumer-group pending list (PEL) to be reclaimed. A duplicate receipt after PostgreSQL commit / Redis ACK failure increments the same unique `(organization_id, redis_entry_id)` occurrence counter; no duplicate evidence row or execution of a rejected command. Conflicting reason replay is rejected.
3. Real Redis 7 `XADD` fixture tests produce a foreign-tenant event, syntactically invalid job ID, and non-existent but valid-format job ID: each gets the correct PostgreSQL reason and successful acknowledgment. The job additionally injects a forced PostgreSQL CHECK rejection: no entry is committed and Redis PEL retains the message. Removing the fault then reclaiming records and acknowledges it. A simulated `XACK` failure after durable PostgreSQL write is repaired by a reclaim with occurrence count 2. The test confirms RLS metadata and read denial for a NOLOGIN tenant reader role.
4. Bounded internal `inspectRejectedSignals({limit})` is tenant-bound and returns only reason, occurrence count and timestamps; max 100 records and no raw payload or public HTTP endpoint. A [pure backoff helper](../../apps/api/synthetic-worker-backoff.mjs) adds a bounded 250ms-exponential ceiling (max 8s) with partial jitter to the **opt-in synthetic standalone worker**. SIGTERM does not force another sleep cycle.

## Explicit limits and open gates

- PostgreSQL and Redis are **not a distributed atomic transaction**. A PostgreSQL write can commit while Redis ACK fails; idempotent replay mitigates the gap but does not prevent all event duplication or Redis data loss. The table is metadata-only rejection history, not a full signed/externally retained dead-letter queue with retry budgets, operator action and audited re-drive.
- The producer is not cryptographically authenticated; Redis Streams signals from a tenant-spoofing actor can be rejected, but this fixture does not prove publisher identity or a hard network perimeter. PG connection currently uses the CI fixture owner/superuser, not a deployed narrowly granted worker identity; no real-host root/cluster recovery or production-grade queue security is proven.
- Normal HTTP authentication remains **SQLite**. No live provider command executes, no host credentials are used, and the standalone synthetic worker remains opt-in and does not auto-start with the API. Full production supervision, multi-instance fencing/policy audit, separate user-facing poison inspection/re-drive approvals, incident alerting, job queue restore and verified provider authorization remain blockers.
- ORB-004 remains `testing / integration_tested` and ORB-005 remains open. This evidence does **not** approve the PostgreSQL auth cutover or production worker deployment.
