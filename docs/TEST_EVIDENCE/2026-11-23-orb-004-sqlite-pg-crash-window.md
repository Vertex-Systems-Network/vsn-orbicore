# ORB-004/005/016/017 — interrupted SQLite v7 and PG16 active-job staging

**Date:** 2026-11-23 UTC. **Status:** Functional PR head `bc1457a06ad7c7f4a3faec59cbf5a7cf86b0f720` passed hosted Node, service integration and task ledger; final documentation-head CI and merge pending. **No production recovery or cross-database atomic commit claimed.**

## Why this gap matters

Prior hosted tests proved a PostgreSQL lease backend rollback and post-commit durability and a separate private quarantined SQLite snapshot parity check, but these did **not** include a process termination at either boundary while **file-backed SQLite** and **PostgreSQL** were both involved. Source/target transactions do not share an atomic commit. In addition, the current application has a genuine `createApp` crash-startup behavior: any SQLite `running` job is changed to `queued` with `error='recovered_after_restart'`. That source state cannot be naively replayed from the earlier PG quarantine metadata.

## Strict CI-only test

- Workflow `.github/workflows/ci-services.yml` adds an isolated **28th** PG16 job, `postgres-ci-cross-store-crash`, running `scripts/verify-postgres-ci-cross-store-crash.mjs` with a fresh PostgreSQL16 container and a temporary file-backed SQLite v7 fixture. It requires exact `GITHUB_ACTIONS=true`, `ORBICORE_CI_ACTIVE_QUARANTINE=1`, `ORBICORE_CI_CROSS_STORE_CRASH=1`, `ORBICORE_CI_NO_PROVIDER_CALLS=1`, loopback PG host, PostgreSQL port 5432, fixture database/user and *hardcoded synthetic CI password*. The integration script never calls cPanel, Redis or a live provider.
- Parent fixture creates two tenants, mock-fixture accounts and users with reserved `.test/.invalid` addresses, one queued and one running active `inventory_refresh` source job with tenant-scoped `ci-queue-*` idempotency. A 32-byte ephemeral HMAC key and witness are retained only in the parent process; the child receives neither.
- **Window A:** Actor A opens persisted SQLite directly (no application restart), stages into PG's private `orbicore_ci_quarantine.active_jobs`, intercepts just the PG `COMMIT` query and reports that its inserts are still uncommitted. Parent sends real Node `SIGKILL`. A separate PG connection waits for the transaction's advisory lock, then verifies **0** quarantine rows and **0** public operational data. A new raw SQLite connection reads all source job fields unchanged.
- **Window B:** Actor B opens the *same* persisted SQLite source and finishes the strictly gated PG staging transaction, then reports that PG committed but no source acknowledgment exists. Parent kills the actor with `SIGKILL`. Fresh raw SQLite reopen must match original source, PG's private quarantine must have 2 rows, the detached signed witness read-only recheck must match, and a second staging attempt must fail due to occupied target.
- After PG commit, an independent SQLite source-key update must be rejected **before opening PostgreSQL** by the existing signed source-digest gate. A manual restoration of the fixture key recovers read-only source-to-PG parity.
- **Real SQLite app restart:** The parent finally starts the actual app against that file-backed DB with worker disabled. Existing app startup requeues the source `running` row, records `recovered_after_restart`, and the old quarantine witness must no longer reconcile even to a fake PG client that would throw if contacted. PG private rows stay 2; `public.jobs`/`public.job_outbox`, public identity and account tables remain zero.
- `tests/ci-cross-store-crash.test.mjs` adds two gate tests that reject missing CI/environment opt-ins, an external PostgreSQL host or changed synthetic PG password without contacting the DB.

## Explicit limitations and interpretation

The setup deliberately models process death **around PG commit**, not a distributed transaction coordinator, true host power loss, WAL fsync guarantees, offsite backup or atomic source/target authority transition. The parent controls exactly when actors are killed using IPC. A queued source may be safely *read* across the PG commit boundary in the mock but may **never** be executed based on that metadata alone. A running source job may have unknown provider effects; this test has no provider, no Redis event, no worker replay and no human approval. The app-startup source requeue and old witness mismatch demonstrate an important production risk, **not** resolution of idempotent effects, lease ownership or dual-write fencing. CI signing keys are ephemeral, not externally anchored. Canonical ORB-004/016/017 remain `testing/integration_tested`, ORB-005 `in_progress/integration_tested`; no lifecycle or verification-level upgrade.
