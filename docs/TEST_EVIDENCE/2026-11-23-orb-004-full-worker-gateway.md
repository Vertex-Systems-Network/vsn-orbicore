## Verified properties

1. Additive, explicitly CI-gated [migration 016](../../db/migrations/016_postgres_ci_worker_gateway.sql) creates a restricted `NOLOGIN NOINHERIT NOBYPASSRLS` intermediary role, a privately administered authenticated PostgreSQL login→tenant mapping, and a set of fixed-schema, fixed-search-path SECURITY DEFINER functions for outbox reservation/confirmation, reconciliation, job status, exact signaled-job claim, lease-fenced finalization and expired-job failure. PUBLIC EXECUTE is revoked **within the create transaction**; migration reapplication succeeds.
2. [Scoped adapter](../../apps/api/ci-scoped-worker-gateway.mjs) and [existing synthetic Redis consumer](../../apps/api/synthetic-redis-worker.mjs) can opt into **the same real non-owner PostgreSQL session for all job/outbox/lease operations**, plus previous restricted metadata-only rejection inspection and recording. Default app/standalone-worker runtime is unchanged. Hosted test used **three actual PG login accounts** (two tenant-bound and one unprivileged) with CI-generated ephemeral passwords, no actual user verifier, and a restricted session with no raw jobs/users/accounts/outbox/secret/rejection/mapping table permissions.
3. Tenant B could not get tenant A's job, claim or fail its jobs, publish its outbox or read A's rejection history. Setting a caller-controlled tenant GUC did not change `session_user` tenant assignment. Both general role escalation and helper-function direct EXECUTE were denied.
4. The restricted outbox-publish transaction holds `FOR UPDATE SKIP LOCKED` **over** the Redis `XADD`, confirms a concrete stream ID and commits only after success; deliberate Redis failure rolled back PostgreSQL `published_at`. A prior Redis deletion was recovered by limited PostgreSQL outbox reconciliation and safe republish.
5. A signaled mock job finished through scoped claim→atomic actor/account policy recheck→hard-coded `live:false` JSON result, while viewer and newly disabled actors failed. Fresh PG actor/account rows are read/locked in the same transaction as job completion; stale claim tokens failed after lease replacement. An EXECUTE grant revocation caused finalization failure without Redis `XACK`, keeping the event in PEL; restoring grant and expiring the lease enabled reclaim and a fenced retry. Explicit max-attempt expiry also worked.
6. A forged tenant Redis wakeup was durably recorded through the **same nonowner SQL session** via restricted metadata-only rejection gateway before being ACKed. No untrusted job payload, actor secret, remote command or provider login is accepted by the restricted function API.

## Scope and limitations

- **This is a CI fixture, not production worker activation.** The ordinary opt-in standalone worker still uses its historical privileged PG connection unless explicitly refactored/provisioned later. The restricted adapter is CI-gated; no production key/role provisioning or live PostgreSQL auth cutover was enabled.
- A privileged schema owner retains the ability to modify SQL function bodies and tenant mappings. `SECURITY DEFINER` does not itself prove independent administration; production needs owner/key separation, trusted migration process, a dedicated runtime identity, genuine actor policy from migrated source records, audit of SQL function changes and a full off-host recovery procedure.
- The Redis `XADD`/PG commit **cannot be a distributed atomic transaction**. If Redis succeeds but PG commit fails, duplicate wakeups are possible and must be controlled through lease fencing and idempotency. Cross-host power-loss, Redis AOF loss, hostile producer identity, distributed supervision, full DLQ redrive, raw provider authorization, and true multi-instance load were not validated.
- This proof establishes **synthetic end-to-end permissions**, not production-ready cPanel/WHM capabilities. No live provider actions, real customer credentials, independent WORM audit/backup, real secret key custody, PostgreSQL production HTTP login authority or rollback of a deployed auth migration.
- ORB-004 remains `testing/integration_tested`; ORB-005 remains `in_progress`. Recommended next: operator-approved dedicated runner logins, signed publisher origin and replay budget, production-grade queue alert/DLQ policy and authorized end-to-end SQLite v7 migration plus durable recovery.
