## What is tested

1. **Versioned additive PostgreSQL auth schema:** `db/migrations/004_postgres_auth_state.sql` adds passkeys, WebAuthn challenges, encrypted TOTP authenticator records, hashed recovery codes, login challenges, notification delivery outbox and recovery contacts, each with a `(user_id, organization_id)` composite FK to prevent cross-tenant records; also a global bootstrap-token schema. The migration can be applied repeatedly on a disposable PostgreSQL target.
2. **RLS and credential-column confinement:** RLS enabled on all seven tenant auth-state tables, with restricted non-secret metadata read policies on passkeys, notification records and recovery contacts for `orbicore_tenant_readonly` (a NOLOGIN/NOBYPASSRLS proof role). Unauthorized queries for passkey public key, TOTP encrypted secret, recovery hash, WebAuthn challenge, login token hash, notification recipient, recovery contact address and bootstrap token hash are denied. Read-only role mutation is denied. Cross-tenant FK insert is rejected.
3. **Guarded synthetic-only, offline, empty-target import:** `copySyntheticIdentityWithAuthSnapshot` requires specific `fixture_only_auth_offline_copy` consent, GitHub Actions CI gate and a synthetic-import environment gate. Source requires mock accounts, `.test`/`.invalid` user/contact/recipient addresses and explicit dummy auth-material prefixes, no existing source jobs, no secret references/active bootstrap tokens and valid SHA-256 audit chain. Data is copied in one PostgreSQL SERIALIZABLE transaction along with organizations/users/accounts/sites/sessions/audit. Auth tables derive tenant IDs from each user's source organization, and count verification spans all copied tables.
4. **Transactional rollback:** a deliberately negative passkey counter in SQLite (valid there but violating PostgreSQL `counter >= 0`) causes a real PostgreSQL constraint failure; rollback leaves organizations, users, accounts, sessions, audit, passkeys, authenticator, recovery and notifications empty. Correcting the source counter then permits full copy. Source SQLite remains unchanged.
5. **Post-copy policy checks:** PostgreSQL MFA-enabled session is denied until marked MFA-verified, tenant A/B receive only their own passkey metadata, and a second import into a nonempty destination is refused. The new additional guard refuses an existing destination bootstrap token.
6. **Unchanged client controls:** normal app HTTP auth stays SQLite and Chromium passkey virtual-authenticator tests remain passing. No provider credentials, real hostnames or delivery endpoints were used; no external hosting action occurred.

## Limitations and incomplete gates

- **NOT production SQLite v7 parity/cutover.** The importer copies a bounded set of *synthetic* core and auth tables, not remaining SQLite v7 feature tables (capability/migration/storage/WordPress/automation/snapshots or secret references) or live data. It intentionally refuses source jobs and unsupported security state; the target receives no live bootstrap tokens or secrets.
- The passkey public keys and TOTP encrypted values are explicitly labeled **fake fixtures**. Successful column round-trip does NOT prove production cryptographic key migration, decryptability after key rotation, correct WebAuthn RP ID/attestation/credential counter handling or MFA replay protection against PostgreSQL.
- PostgreSQL database owner still performs fixture inserts; RLS proof uses a restricted NOLOGIN read-only role but **no trusted production write role or HTTP identity cutover**. A custom tenant GUC is not a sufficient security boundary for untrusted direct SQL users.
- There is no atomic cross-database SQLite/PostgreSQL cutover, off-host recovery, distributed session revocation, real notification service or authorized live cPanel/WHM test. New runtime MFA endpoints, multi-node consistency and live provider safety remain open.
- **Project lifecycle:** ORB-005 stays `in_progress / integration_tested`. ORB-004 and ORB-016 remain `testing / integration_tested`.
