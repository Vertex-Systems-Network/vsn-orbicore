## Verified in hosted PG16/Redis7 fixture

1. Explicitly CI-gated [HMAC signer/verifier](../../apps/api/ci-wakeup-attestation.mjs) generates deterministic domain-separated HMAC-SHA256 over `[version, organization_id, job_id, outbox_uuid]`, using injected 32-byte-or-longer **in-memory-only** key and a bounded nonsecret key ID. `timingSafeEqual` verifies the MAC. The verifier accepts exactly five allowlisted fields; unknown keys, modified tenant/job/UUID/MAC, extra Redis fields, `__proto__` and duplicate-field ambiguity fail closed. A second key may verify old events only while explicitly held as a previous key; removing that key denies it.
2. In the opt-in **restricted** synthetic worker, [scoped job gateway](../../apps/api/ci-scoped-worker-gateway.mjs) signs metadata before `XADD` and confirms the actual Redis **server-assigned stream entry ID** in the committed PostgreSQL outbox transaction. New [migration 017](../../db/migrations/017_postgres_ci_signed_wakeup.sql) adds a `SECURITY DEFINER` function restricted to the verified nonowner worker function role and authenticated tenant mapping. It requires matching tenant+job+outbox UUID+exact Redis entry ID in **committed** PG state. An old HMAC copied into a different Redis stream entry fails even though the HMAC itself remains valid.
3. [Synthetic Redis consumer](../../apps/api/synthetic-redis-worker.mjs) checks HMAC *and* the PostgreSQL outbox binding **before querying, claiming or completing a job**. Missing/tampered/unknown-key signatures are rejected as `invalid_signature`; MAC-valid but unanchored/replayed events are rejected as `outbox_mismatch`. Both outcomes are recorded in an existing tenant-bound, metadata-only PostgreSQL rejection table **before Redis ACK**, with no raw Redis fields or job credentials.
4. Real PG16/Redis7 hosted scenarios test unsigned stream forgery targeting an otherwise valid queued job (job remains `queued`, attempts 0); copied valid HMAC on a new Redis ID (outbox mismatch and no second claim); modified signature, key, job and extra/prototype fields; old key accepted with explicit rotation, old key removed and rejected; afterward, recovery through PG outbox reconciliation and new-key republish. A revoked PG `validate_wakeup` function EXECUTE privilege fails without XACK, keeps the Redis message pending in PEL and succeeds on reclaim after grant restored.
5. The fixture uses two real authenticated, NOINHERIT/NOLOGIN-gateway PostgreSQL tenant-bound SQL principals; copying a valid tenant-A signed envelope onto tenant B's Redis stream fails PostgreSQL outbox tenant binding and never executes tenant A's job. No plaintext credential, private signing key, real provider operation or production HTTP auth traffic was used.

## Remaining risks and nonclaims

- **No production cryptographic publisher identity:** the signing key exists only inside one disposable CI test runner. No independently administered KMS/HSM, secure shared key-rotation distribution across actual worker processes, operator audit/custody, Redis ACL/mTLS or durable cross-restart key access is implemented. A compromised signer/worker can issue fully valid signatures, and the pipeline's trusted PostgreSQL schema owner can alter outbox receipts.
- Redis and PostgreSQL do not share an atomic transaction; a Redis `XADD` may commit before an unsuccessful PostgreSQL confirmation, leaving an orphan that this gate rejects but which still needs reconciliation. A valid message may be delivered multiple times using its original Redis ID and must remain job-lease-fenced/idempotent. No distributed fleet, power-loss, AOF fsync or offsite object-lock proof.
- The signed mode is **CI-only injection**: normal standalone synthetic worker remains on historical path and production HTTP remains SQLite-authoritative. This signature does not authorize provider commands, prove user consent, migrate full SQLite identities/secret references, establish external WORM backup or approve PostgreSQL login cutover.
- ORB-004 stays `testing/integration_tested`. Next: independently managed worker identity/signing-key custody, authenticated producer network boundary, signed-key rotation under restart, replay budget/rate-limit incident policy, operator-approved DLQ/redrive, full identity/backfill and secure disaster recovery.
