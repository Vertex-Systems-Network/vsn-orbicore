## What the implementation proves

1. **Restricted PostgreSQL-only password verifier:** migration `008_postgres_ci_auth_lifecycle.sql` creates `pgcrypto`-backed bcrypt verification **only for explicitly tagged `ci_pg_bcrypt_only` records**. This is not a port of SQLite's scrypt password format; the hosted test seeds and refuses a record marked as a non-CI legacy credential, even when its stored hash is otherwise a valid bcrypt string. The function returns only a boolean outcome, tenant and MFA-required flag, never password hashes or salts.
2. **Live PostgreSQL session issuance:** `apps/api/postgres-ci-login.mjs` uses the real disposable **non-owner, NOINHERIT, NOBYPASSRLS** PostgreSQL login and transaction-local `SET ROLE orbicore_synthetic_submitter`. It generates a cryptographically random 32-byte cookie token locally and sends only its SHA-256 hash to a restricted SQL function. The SQL inserts a new scoped session with one-hour expiry or, for users requiring MFA, a **five-minute pending session** that cannot authorize jobs.
3. **Browser-style cookie/CSRF interface:** existing **CI-only loopback** HTTP harness now optionally exposes `POST /__ci/pg/auth/login`, `POST /__ci/pg/auth/mfa/recovery`, and `POST /__ci/pg/auth/logout`. Login sets `HttpOnly; SameSite=Strict; Path=/` with a bounded Max-Age; pending MFA has a cookie-bound process-secret HMAC CSRF token. Active sessions obtain their existing cookie-bound CSRF token from the PostgreSQL-backed GET endpoint. Mutations require same-origin and CSRF checks; raw session values never appear in the JSON response or evidence. **Secure is omitted only because this disposable fixture runs on HTTP loopback.**
4. **One-time recovery-code MFA:** `recovery_codes` SHA-256 hashes are verified and marked consumed in one PostgreSQL transaction. Successful recovery rotates the session token and expands expiry to one hour; the original pending cookie no longer works. A used code cannot authenticate a second login. Five incorrect codes revoke the pending session without consuming an unused valid code. This is explicitly a **recovery-code proof, not a TOTP/passkey cryptographic migration**.
5. **PostgreSQL-backed login throttling:** a per-email SHA-256 pseudonymized throttle row tracks failed password attempts; five failures lock the identifier for 15 minutes. Tests demonstrate a correct password during lockout cannot bypass it. The hash is **not a keyed pseudonym**, so production protection from offline email enumeration, cross-IP abuse, timing differences and distributed denial-of-service requires additional design.
6. **Fresh actor and tenant authorization:** viewer login may succeed, but the restricted synthetic job writer correctly refuses it; disabled accounts cannot log in. Origin spoofing, missing/incorrect session-bound CSRF, cross-tenant accounts and provider-backed accounts are all denied. Session/logout revocation and later user disabling are immediately enforced via fresh PostgreSQL session+user joins; the write transaction independently verifies actor/MFA/account permissions.
7. **Logout and replay:** CSRF-protected logout deletes the PostgreSQL session and returns a cookie with `Max-Age=0`. Replaying the old session cookie or its previous CSRF token cannot authorize work. A different session cannot borrow another user's CSRF token. Direct SELECT of passwords, recovery hashes and session-token hashes—and direct calls to protected SQL functions—are denied to the restricted non-owner login.
8. **No changes to existing HTTP auth:** the application `createApp`/default `npm start` still authenticates against SQLite. The fixture is not mounted into it. Existing PG synthetic job/outbox/audit, Redis worker, Compose recovery and Chromium checks passed without modification.

## Boundaries and remaining verification

- **Not production password compatibility:** existing SQLite users use `scryptSync`; this CI-only implementation uses bcrypt with an explicit fixture marker. There is no password migration/cutover, password-reset policy, production credential compatibility or forward/rollback sync.
- **Not production MFA cryptography:** only synthetic recovery-code consumption and session rotation were verified. Real TOTP secret decryption, key custody/rotation, challenge semantics, physical passkey verification, notification delivery and recovery against live identities remain unsupported.
- **Not production cookie/security edge:** this is HTTP loopback, not TLS/HTTPS reverse-proxy hosting. The cookie intentionally lacks `Secure` on loopback. Production `Secure`/domain policy, rotation across instances, anti-enumeration handling, distributed rate limiting, session cleanup and comprehensive refresh-token semantics are not proven. Test authentication and MFA events are not yet inserted into the unified hashed audit log.
- **Not production PostgreSQL authority switch:** normal SQLite HTTP remains unchanged, while the new SQL functions are only called by the opt-in CI harness under a restricted temporary LOGIN. Real database login provisioning, tenant authorization for all runtime write paths, migration of historical jobs/audits/secrets, production backup/restore and a reversible cutover remain open. No real credentials, provider operations, or live account changes occurred.
