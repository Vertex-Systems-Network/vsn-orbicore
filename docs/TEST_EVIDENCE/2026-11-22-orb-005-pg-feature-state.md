## Verified implementation scope

1. **Additive feature-table schema:** `db/migrations/005_postgres_feature_state.sql` adds or extends seven SQLite-v7 operational feature tables: `capability_snapshots`, `migration_plans`, `storage_policies`, `site_snapshots`, `automation_rules`, `automation_runs`, and existing `wp_site_state`. Validated nonnegative/bounded fields and JSON shapes. Reapplying the migration succeeded on a disposable target. A separate hosted upgrade fixture first populated an **old-schema site** and proved that the migration's backfill sets the owning organization correctly before the second DDL run.
2. **Tenant integrity at DB layer:** the PostgreSQL `sites` relation gains an organization column backfilled from accounts, a not-null requirement and composite `(account_id, organization_id)` FK. Account/site/rule references for feature rows also use composite tenant FKs. Wrong-tenant SQLite snapshot rows (allowed by the source's weaker FK) are **rejected** by PostgreSQL and roll back the whole transaction. A separate cross-tenant automation-rule reference was rejected.
3. **Bounded, synthetic-only offline snapshot:** `copySyntheticFullFeatureSnapshot` needs distinct `fixture_only_features_offline_copy` consent and GitHub-only CI/test-data gates inherited from the auth snapshot. It copies core identity, mock accounts/sites, sessions/audit, MFA/passkey/recovery/notification tables and all seven feature tables in **one PostgreSQL serializable transaction**; SQLite source is held in an exclusive write-preventing `BEGIN IMMEDIATE` snapshot, then rolled back without writes. Existing jobs, secret references, live account sources and nonempty target tables are refused.
4. **Source and target parity:** PostgreSQL row counts matched SQLite per copied table; site organizations were derived from their owning accounts. Operational JSON is stored as its **exact source TEXT**, not lossy JSONB reserialization. Existing SQLite `capabilities_json` fixtures are JSON **arrays**; initial PG constraint mistakenly required objects. Hosted CI identified the mismatch, and migration 005 now validates both array/object shapes while preserving raw text.
5. **Least-privilege read proof:** `orbicore_tenant_readonly` has NOLOGIN/NOBYPASSRLS and tenant-context RLS SELECT policies for operational metadata, with safe-column-only grants. No tenant context yields zero rows; org A/B see only their own records. Attempts to read `sites.document_root`, capability payload JSON, migration preflight JSON, storage endpoints and bucket, site snapshot details, automation run summary, WordPress staging URL, and secret ciphertext were all denied; DELETE on automation rules was denied.
6. **Regression proof:** existing identity, MFA, PG/Redis worker, Compose, and virtual-WebAuthn jobs passed. Four added unit tests validate fixed feature-table identifiers, exact JSON source preservation, boolean coercion, invalid snapshot guard and distinct consent. Existing fixture operational tables are already populated; hosted verification compares all original rows instead of incorrectly expecting one seeded row (a second CI-detected test assumption fixed before green checkpoint).

## Explicit limits and remaining gates

- **Not a production SQLite v7 cutover.** HTTP auth, jobs, inventory and audit remain SQLite-backed in the running application, unless explicitly injected into prior test-only slices. There is no cross-store atomic authority switch, write/failover integration or production job replay. `schema_migrations` SQLite bookkeeping is not a PostgreSQL migration runner.
- **Not a live provider migration.** No production secrets, real TOTP key material, live passkeys, credentials, cPanel/WHM/S3 accounts or notifications were accessed or copied. Job history and `secret_references` are still deliberately refused, and production key-decryptability/custody requires separate proof.
- **Runtime PostgreSQL identity clients are not yet adapted** to `sites.organization_id`: migration 005 requires it on all future PostgreSQL site inserts. Future real repository code must supply the tenant. The existing application HTTP path remains SQLite and is unaffected.
- The NOLOGIN RLS role is a **database read-security proof**. GitHub schema owner/superuser inserts bypass RLS; trusted non-bypass runtime **write** roles and actor-context security are unimplemented. A caller-settable GUC alone must never be trusted as a tenant security boundary.
- Off-host backup/restore, abrupt host failure, multi-node failover, active sessions on cutover, physical authenticators and owner-authorized live provider calls remain unverified.
- **Lifecycle:** ORB-005 stays `in_progress/integration_tested`. ORB-004 and ORB-016 remain `testing/integration_tested`.
