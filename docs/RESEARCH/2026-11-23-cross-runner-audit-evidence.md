# ORB-005 — CI-only cross-runner audit metadata custody and recovery exercise

**Reviewed:** 2026-11-23. **Scope:** Rehearsal only. There is no production backup, identity migration, provider operation, external vault or WORM storage.

The prior [CI-only detached checkpoint](../TEST_EVIDENCE/2026-11-23-orb-005-ci-detached-readiness.md) was a writable file on the same runner as its SQLite and PostgreSQL fixture. This slice uses a separate GitHub Actions job runner to test **transport, evidence authentication, and metadata-only reconstruction**:
- Producer builds random synthetic, password-free source epoch/event and matched PostgreSQL-shaped witness metadata. Node.js [Ed25519](https://nodejs.org/api/crypto.html#cryptogeneratekeypairsynctype-options) generates a distinct signing pair **in memory**. The private key is never serialized. An [SPKI public key](https://nodejs.org/api/crypto.html#keyobjectexportoptions), public-key SHA-256 fingerprint, and signed canonical metadata are exportable.
- Signed evidence is transferred via [GitHub Actions artifacts v4](https://github.com/actions/upload-artifact), while the expected public-key SHA-256 fingerprint, artifact SHA-256 and checkpoint sequence go separately through a producer job output. The consumer uses [download-artifact v4](https://github.com/actions/download-artifact) on a **fresh job runner**, checks the trusted outputs, verifies Ed25519 signature and complete synthetic source epoch/witness matching, rejects extra fields that could contain account verifiers, and reconstructs three narrow SQLite metadata tables in one transaction. Injected restore exceptions roll back the transaction.
- All fixture fields are synthetic opaque IDs, non-secret HMAC-shaped random values, reason codes and epochs. The consumer does **not** verify the original source HMAC (the source signer key is intentionally unavailable); Ed25519 only authenticates the archived snapshot against the separately communicated public-key pin. No password, session cookie, login verifier, recovery key, private signing key, MFA material or provider credential is archived.
- A signed snapshot can be old or incomplete *before signing*. The job output and artifact are administered by the same workflow/repository, so this is **not an independent security principal**, operational key rotation, external KMS/HSM or immutable/object-locked audit retention. GitHub Actions artifacts have finite retention and are mutable/deletable by authorized workflow administrators; they are not off-host database snapshots or WORM.
- Independent job runner **is not independent organization/admin authority**. Source SQLite, PostgreSQL jobs/secrets, encryption-key custody, live HTTP authentication and restoration of actual user identities are **not** backed up or restored. No power-loss, object-store account compromise, cross-region recovery or cold-start cutover was proven.

**Production exit requires** independently managed WORM/object-lock destination plus retention/immutability tests, well-defined owner/IAM and key custody (including recovery and rotation), verified full encrypted SQLite v7/PG jobs/secrets backup and off-host restore with consent, real MFA-aware actor audit and human-approved fail-closed cutover/rollback. Ordinary HTTP login stays SQLite.
