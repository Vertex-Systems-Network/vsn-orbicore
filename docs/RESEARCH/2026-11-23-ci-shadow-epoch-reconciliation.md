# ORB-005 — CI-only source change outbox and monotonic PG invalidation

**Recorded:** 2026-11-23. The following design is a test-only continuation of ADR-0003; it does not justify production authentication cutover.

- [SQLite transactions](https://www.sqlite.org/lang_transaction.html) and [SQLite isolation](https://www.sqlite.org/isolation.html) establish that a source credential mutation plus corresponding outbox event can be committed in **one SQLite transaction**, unlike a SQLite/PG distributed transaction. The CI test uses a file-backed SQLite fixture for reopen/retry. **No OS-level power loss, kernel crash, disk corruption, WAL fsync, or off-host restore is tested.**
- [PostgreSQL 16 explicit locking](https://www.postgresql.org/docs/16/explicit-locking.html) documents row locking. The prior restricted staging function selects the synthetic PG `users` row `FOR SHARE`, while the new invalidation function obtains `FOR UPDATE` on that same row. These accesses serialize staging/reconciliation per user. A BEFORE INSERT trigger then consults the reconciled source-epoch fence, rejecting old synthetic drafts.
- [PostgreSQL 16 security-definer functions](https://www.postgresql.org/docs/16/sql-createfunction.html) and [RLS](https://www.postgresql.org/docs/16/ddl-rowsecurity.html) require trusted owner/safe `search_path` plus limited caller EXECUTE grants. The new private fence table forces RLS with zero policies; a separate NOLOGIN reconciler role can invoke a **revoke-only** function but cannot read or stage credential hashes.
- One-way source outbox records contain only tenant/user identifiers, epoch, event ID, event reason and pending/reconciled status. The restricted PostgreSQL reconciler **cannot independently attest** that an SQLite event exists. Production requires verifiable source-ownership/provenance and poisoning/replay governance.
- A successful PG invalidation followed by an interrupted SQLite acknowledgement leaves a pending event. Retrying the same event is idempotent; a later applied epoch can safely acknowledge an older pending event, but the PG high-water mark never decreases. Shadow credentials remain totally inert. Any stale shadow after a source update and before PG reconciliation remains **unsafe to use**; there is no production read gate or cutover switch.

**Risk register:** Mutable SQLite fixture tables and CI-only flags do not model real authenticated password/reset/disable/MFA endpoints, hardware passkeys, signing/key custody, distributed reconciliation lease/acks, external durable audit, SIEM alerting, production DB migrations, or recovery after disk/power loss.
